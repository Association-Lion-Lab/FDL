# FDL `acces` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pendant la bêta, seules les personnes invitées entrent sur FDL : elles créent leur compte depuis un lien d'invitation, se connectent par mot de passe avec une double authentification facultative (obligatoire pour modérateurs et administrateurs), et les administrateurs gèrent invitations et comptes sous `/admin`.

**Architecture:** Même processus Node que le `socle`, sans framework. Pages HTML rendues côté serveur avec de simples formulaires ; le seul JavaScript client sert aux clés d'accès. Sessions par cookie opaque dont seul le hachage SHA-256 est stocké en base. Un seul mécanisme de lien à usage unique sert aux invitations et aux réinitialisations d'accès. Les connexions sensibles sont écrites dans un fichier journal séparé sur la machine.

**Tech Stack:** Node.js >= 22, `node:crypto` (scrypt, hachages, aléa), PostgreSQL 18 via `pg`, `@simplewebauthn/server` 14.0.3, `@simplewebauthn/browser` 14.0.0, `otpauth` 9.5.2, `uqr` 0.1.3 (QR code en SVG, sans dépendance).

**Spec:** `docs/superpowers/specs/2026-10-27-fdl-cahier-des-charges-design.md` (sections 3, 5, 9, 10, 13). Décisions du porteur de projet prises le 27 octobre 2026 pour cette tranche :
- membres : mot de passe, double authentification facultative ;
- modérateurs et administrateurs : mot de passe + clé d'accès obligatoire, TOTP en secours facultatif, codes de récupération ;
- alertes de connexion admin : un fichier journal séparé sur la machine (pas d'e-mail, fournisseur non choisi) ;
- invitations : lien copié à la main par l'administrateur ;
- mot de passe oublié : un admin crée un lien de réinitialisation et le transmet à la main ;
- aucun secret stocké en clair : le secret TOTP est chiffré avec une clé qui ne vit ni en base ni dans les sauvegardes ;
- QR code pour activer le TOTP ;
- bêta : un invité connecté a accès à toutes les fonctions ; seuls les visiteurs non connectés sont bloqués.

## Global Constraints

- Tout ce qui figure dans les Global Constraints du plan `socle` reste valable (Node `>=22`, `node:test`, erreurs JSON, variables `PG*`, aucun secret journalisé, tests sur `127.0.0.1:0` avec une base jetable, `npm run test:docker` comme référence).
- Dépendances approuvées par ce plan, et elles seules : `@simplewebauthn/server@^14.0.3`, `@simplewebauthn/browser@^14.0.0`, `otpauth@^9.5.2`, `uqr@^0.1.3`. Aucune cryptographie écrite à la main : mots de passe avec `crypto.scrypt`, chiffrement avec `crypto` en `aes-256-gcm`, aléa avec `crypto.randomBytes`, comparaisons avec `crypto.timingSafeEqual`.
- Aucun jeton, mot de passe, secret TOTP, code de récupération ni cookie dans un journal, une URL de redirection ou une réponse autre que celle qui le montre une seule fois à son propriétaire.
- Toute page HTML échappe le texte venant d'une personne. Aucun script ni style chargé depuis un tiers.
- Seul cookie : la session (`fdl_session`, `HttpOnly; Secure; SameSite=Lax; Path=/`). Pas de bandeau, pas de traceur.
- Tout `POST` dont l'en-tête `Origin` est absent ou différent de `FDL_ORIGIN` est refusé `403 bad_origin`.
- Textes destinés aux personnes en français ; noms anglais dans le code.
- Travail sur la branche `feat/acces`, créée depuis `development` ; rien n'est poussé sans accord explicite.

## Review Focus

1. **Lien d'invitation réutilisé, expiré ou révoqué.** Refus clair, aucun compte créé. Tests dans la Tâche 2.
2. **Double clic sur « Créer mon compte »** (deux requêtes avec le même lien). Un seul compte. Test dans la Tâche 2.
3. **Nom affiché contenant du HTML** (`<script>`), vu dans `/admin`. Le texte est échappé. Tests dans les Tâches 3 et 8.
4. **Compte banni avec une session encore ouverte.** La requête suivante est refusée et la session supprimée. Test dans la Tâche 3.
5. **Code TOTP rejoué** dans la même fenêtre de 30 s. Refusé. Test dans la Tâche 5.

### Tâche 2 : Mots de passe, liens à usage unique, création de compte

**Files:**
- Create: `src/accounts.js`, `scripts/invite.js`, `tests/accounts.test.js`
- Modify: `package.json` (`"invite": "node scripts/invite.js"`)

**Interfaces:**
- Produces (dans `src/accounts.js`) :
  - `hashPassword(password: string) => Promise<string>` : `scrypt` avec `N=32768, r=8, p=1, maxmem=64 MiB`, sel 16 octets, clé 64 octets ; format `scrypt$32768$8$1$<sel base64>$<hachage base64>`.
  - `verifyPassword(password, stored) => Promise<boolean>` : relit les paramètres du format, compare avec `timingSafeEqual`.
  - `checkPassword(password) => string | null` : message français si moins de 12 ou plus de 256 caractères, sinon `null`.
  - `hashToken(token: string) => Buffer` (SHA-256). Réutilisé par les sessions et les codes de récupération.
  - `createLink(db, { kind, role?, accountId?, note?, createdBy? }) => Promise<string>` : jeton de 32 octets aléatoires en base64url, seul son hachage est stocké ; expire dans 14 jours.
  - `redeemInvitation(db, { token, email, displayName, password }) => Promise<{ accountId } | { error: 'link_invalid' | 'email_taken' }>`
  - `redeemReset(db, { token, password }) => Promise<{ accountId } | { error: 'link_invalid' }>` : change le mot de passe, supprime sessions, TOTP, clés d'accès et codes de récupération du compte.
- `scripts/invite.js` : `npm run invite -- <role>` (défaut `member`). Il crée une invitation et affiche `<FDL_ORIGIN>/inscription?code=<jeton>`. C'est le seul moyen de créer le premier administrateur.

Règle de consommation : un seul `UPDATE access_links SET used_at = now() WHERE token_hash = $1 AND kind = $2 AND used_at IS NULL AND revoked_at IS NULL AND expires_at > now() RETURNING ...`, dans la même transaction que la création ou la modification du compte. Une violation d'unicité sur l'e-mail annule tout (le lien reste utilisable) et renvoie `email_taken`.

- [ ] **Step 1: Tests en échec** :
  - `verifyPassword('correct horse battery', await hashPassword('correct horse battery'))` → `true` ; avec un autre mot de passe → `false` ; deux hachages du même mot de passe diffèrent.
  - `checkPassword('court')` → message ; `checkPassword('x'.repeat(12))` → `null`.
  - invitation consommée deux fois → 2e appel `{ error: 'link_invalid' }`, un seul compte.
  - deux `redeemInvitation` lancés en parallèle (`Promise.all`) avec le même jeton → exactement un succès, un seul compte.
  - invitation expirée (forcer `expires_at` dans le passé) ou révoquée → `link_invalid`.
  - e-mail déjà pris en casse différente → `email_taken`, et l'invitation reste utilisable.
  - le compte créé porte le rôle de l'invitation ; la table ne contient pas le jeton en clair.
  - `redeemReset` change le mot de passe et vide `sessions`, `totp_secrets`, `passkeys`, `recovery_codes` du compte.

### Tâche 5 : TOTP et codes de récupération

- Pages :
