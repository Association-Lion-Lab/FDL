# FDL `socle` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Une instance FDL démarre avec une configuration validée, ouvre et migre sa base PostgreSQL, répond à `/health` et `/ready`, se sauvegarde puis se restaure sans perte, et se déploie et se met à jour avec Docker Compose.

**Architecture:** Un seul processus Node (`node:http`, sans framework). La configuration est lue une fois au démarrage, puis tout échec avant `listen` arrête le processus. PostgreSQL est accédé avec `pg`. Les migrations sont des fichiers SQL numérotés, appliqués tous ensemble dans une seule transaction. Sauvegarde et restauration sont des scripts Node qui pilotent `pg_dump` et `pg_restore`, avec un manifeste de sommes SHA-256.

**Tech Stack:** Node.js >= 22, modules ES, `node:test`, PostgreSQL 18, `pg` 8.x (première dépendance, approuvée par ce plan), Docker Compose, Caddy 2.

**Spec:** `docs/superpowers/specs/2026-10-27-fdl-cahier-des-charges-design.md`. Il prime sur `SPEC-socle.md`, qui reste valable pour le reste : contrats de configuration, de santé, d'erreurs, de sauvegarde et de restauration, ainsi que la stratégie de tests.

## Global Constraints

- Node `>=22` ; `"type": "module"` ; tests avec `node:test` et `node:assert/strict` uniquement.
- Seule dépendance autorisée par ce plan : `pg`. Toute autre dépendance doit être demandée avant.
- Noms anglais dans le code, messages destinés aux personnes en français, deux espaces, points-virgules, aucune abstraction créée pour un seul appel.
- Erreur JSON : `{ "error": { "code": "<stable>", "message": "<français>" } }`, plus `requestId` pour les erreurs internes uniquement.
- Aucun secret (mot de passe PostgreSQL) dans une URL, une réponse HTTP ou un journal.
- Accès base par les variables standard de `pg` : `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`. Pas de `DATABASE_URL`.
- Tests HTTP uniquement sur `127.0.0.1` avec le port `0` ; chaque test qui touche la base utilise sa propre base jetable.
- La commande de référence est `npm run test:docker` (Tâche 0b) ; elle passe sans test ignoré. `npm test` tourne dans le conteneur ; lancé hors du conteneur sans `PGHOST`, il échoue avec un message clair.
- Dans ce plan, chaque « `npm test` → PASS » se lit « `npm run test:docker` → PASS ».
- Données d'exécution, sauvegardes, `.env` et `.superpowers/` jamais dans Git.
- Travail sur la branche `feat/socle` ; rien n'est poussé sans accord explicite.

## Review Focus

1. **`FDL_DATA_DIR` relatif ou inexistant.** On attend un refus avant l'écoute, sans créer de dossier au mauvais endroit. Test ajouté dans la Tâche 1.
2. **PostgreSQL injoignable au démarrage.** On attend la sortie code 1, un message en français, et aucun mot de passe dans la sortie. Test ajouté dans la Tâche 5.
3. **Restauration vers une base ou un dossier de données non vide.** On attend un refus sans aucune modification. Test ajouté dans la Tâche 7.
4. **Sauvegarde interrompue** (par exemple `pg_dump` absent). On attend qu'aucun dossier ne puisse passer pour une sauvegarde valide : le manifeste est écrit en dernier, et la restauration refuse un dossier sans manifeste. Tests ajoutés dans les Tâches 6 et 7.
5. **Deux processus qui migrent en même temps** (mise à jour lancée deux fois). On attend une seule application des migrations et aucune erreur. Le verrou consultatif est testé dans la Tâche 3.

### Tâche 3 : Base PostgreSQL et migrations

**Files:**

- Modify: `package.json` (`npm install pg`, version résolue notée dans le commit)

**Interfaces:**
- Produces:
  - `createPool(overrides?: { database?: string }) => pg.Pool` (lit les `PG*`)
  - `migrate(pool, { dir?: string } = {}) => Promise<{ from: number, to: number }>`
  - `readSchemaVersion(pool) => Promise<number>` (0 si la table `fdl_schema` est absente)
  - `LATEST_SCHEMA_VERSION: number` (le plus grand numéro trouvé dans `src/migrations`)

- Règles :
  - fichiers `NNNN-name.sql`, triés par numéro ;
  - `fdl_schema(version integer not null)` contient une seule ligne ;
  - toutes les migrations en attente s'appliquent dans **une seule** transaction, après `SELECT pg_advisory_xact_lock(7302231)` ;
  - si la version en base est supérieure à `LATEST_SCHEMA_VERSION`, lever `Error` avec `code = 'schema_incompatible'` et un message en français, sans rien modifier.
- `0001-extensions.sql` : `CREATE EXTENSION IF NOT EXISTS unaccent;` puis création de `fdl_schema`.

  - deuxième appel → `{ from: N, to: N }`
  - deux `migrate` concurrents sur deux pools vers la même base → tous deux résolvent, version finale `N`
  - version forcée à `N + 1` → rejette avec `code === 'schema_incompatible'` ; la version est toujours `N + 1`
  - dossier temporaire avec `0001-ok.sql` (crée une table `t`) et `0002-bad.sql` (SQL invalide) → rejette ; `readSchemaVersion` vaut `0` et la table `t` n'existe pas

### Tâche 7 : Restauration vérifiée

**Files:**
- Create: `scripts/restore.js`, `tests/restore.test.js`
- Modify: `package.json` (`"restore": "node scripts/restore.js"`), `README.md`

**Interfaces:**
- Consumes: `createBackup`, `LATEST_SCHEMA_VERSION`, `createTestDatabase`.
- Produces: `restoreBackup({ config, database: string, backupDir: string }) => Promise<void>`. **Avant toute modification**, il vérifie dans cet ordre, et lève `Error` avec un `code` stable et un message en français :
  1. `manifest.json` présent et `format === 1` → sinon `backup_invalid`
  2. chaque somme du manifeste correspond, et aucun fichier n'est manquant → sinon `backup_corrupted`
  3. `schemaVersion <= LATEST_SCHEMA_VERSION` → sinon `schema_incompatible`
  4. base cible vide (aucune table hors `pg_catalog` et `information_schema`, aucune extension autre que `plpgsql`) et `dataDir` vide → sinon `target_not_empty`

  Ensuite : `pg_restore --exit-on-error --single-transaction --no-owner --dbname=<database>`, puis copie de `files/` vers `dataDir`.
- CLI : `npm run restore -- <backupDir>`.

- [ ] **Step 1: Tests en échec :**
  - aller-retour : sauvegarde d'une base A remplie, restauration vers une base B vierge et un `dataDir` vierge → même `readSchemaVersion`, mêmes lignes dans la table de test, même contenu de `photos/a.jpg`
  - un octet modifié dans `database.dump` → `backup_corrupted` ; la base B est toujours vide
  - `manifest.json` absent → `backup_invalid`
  - `schemaVersion` du manifeste à `LATEST + 1` (somme recalculée pour isoler le cas) → `schema_incompatible`
  - base cible contenant une table → `target_not_empty` ; la table et ses lignes sont intactes
- [ ] **Step 2:** `npm test` → FAIL.

  La base n'a pas besoin d'être restaurée : toutes les migrations d'une version tiennent dans une seule transaction, donc une migration ratée ne laisse rien.
